## 1. 原始需求复述

用户是上海大学数字媒体技术专业学生，在准备 AIGC / 数字人方向的作品集项目。参考 GitHub 项目 **HAST-SEC**（武汉光影流明：本地中文交互角色演示，0.8B 小 LLM + 小型运动模型 + VRM 驱动），但其**不开放训练流程**，且**只支持 VRM、不支持 BVH/FBX**，无法用自己手上的动作数据训练。

用户要做一个"形态差不多、但**真的能训练**"的项目：

> 用本地 BVH / FBX 动作数据训练一个模型，实现**中文文本指令操纵人物模型运动**，显存占用越小越好，能在浏览器里实时预览本地 FBX，并能导出到 Unreal Engine。

已知硬件：RTX 3080 Ti（12 GB 显存）、D 盘剩余 334 GB、Windows 11、无 conda / 无 Ollama / 无预装 torch。数据集位于只读网络盘 `Z:/1000hours/`。

## 2. 产品定义

### 2.1 一句话定位

**TTM 是一个"可自己训练的中文文本→骨骼动作"创作工具：喂进你自己的 BVH 动作库，用一句中文说人话（"慢慢走上楼梯"、"打一套长拳"、"挥挥左手"），就生成 5 秒以上的连贯骨骼动画，在浏览器里立刻看到角色动起来，并一键导出 BVH / UE 可用动画。**

### 2.2 产品目标（3 条，正交）

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | **可训练性**（区别于 HAST-SEC 的核心价值） | 用户能用自己的 BVH 数据从零训练出模型；训练脚本、数据管线、配置全部开放且可在 12 GB 显存内跑通 |
| G2 | **中文语义正确性** | 中文指令能被正确理解并映射到动作语义，无需用户学习任何术语或英文 prompt |
| G3 | **可交付性**（作品集可用） | 生成结果能在浏览器实时预览、能导出 BVH 给 Blender、能导出给 UE 直接使用；不是只有 loss 曲线的研究 demo |

### 2.3 成功标准（可验证）

| 编号 | 成功标准 | 验收方式 |
|---|---|---|
| S1 | 输入「上楼梯」，生成 ≥ 5 秒（150 帧 @30fps）动作，语义正确 | 5 名盲评者中 ≥ 4 人给出 ≥ 3/5 分（"能看出在上楼"） |
| S2 | 全流程显存达标 | 训练峰值 ≤ **5 GB**、推理峰值 ≤ **2.5 GB**，`nvidia-smi` 实测记录写入报告 |
| S3 | 端到端可用 | 从输入中文到浏览器可播放 ≤ **10 秒**（含模型加载后热启动）；同一结果导出 BVH 后可被 Blender 正常导入并播放 |

**里程碑约束**：首次跑通小规模训练 → 出第一版可演示效果，全程 ≤ **2–3 小时**（在已完成环境搭建的前提下）。

| ID | 角色 | 我想要 | 以便于 |

## 3. 数据资产（已实地验证）

| `Take_*` 目录数 | **12,038**（平均 2.17 个演员/动作） |
| 帧率 | 约 **120 fps**（`Frame Time 0.00833333`） |
| 单文件帧数 | 数百 ~ 2,850 帧 |
| 路径语义 | 目录层级即语义标签，`<大类>/<子类>/<细类>/<日期>/Take_xxx/Take_xxx_<演员>.bvh` |

### 3.2 数据集 B — `Z:/1000hours/4.wushu`（武术动作）

| 项 | 实测值 |
|---|---|
| `.bvh` | **220** |
| `.fbx` | **228** |
| 总体积 | 约 1.2 GB |
| 类别 | `Changquan1~12`（长拳）、`Chen_style_Tai_Chi1~3`（陈式太极）、`Bajiquan`（八极拳）、`Crane_Fist1~5`（鹤拳）、`Basic_Fist` / `Basic_Sword` / `Basic_Broadsword` / `Basic_Cudgel` / `Basic_Spear`（基本拳 / 剑 / 刀 / 棍 / 枪）、`Competition_Broadsword` 等 |

### 3.3 骨架事实（架构层已确认，本 PRD 不推翻）

**两套 BVH 共用同一套 23 关节骨架：**

```
Hips, Spine, Spine1, Spine2, Spine3, Neck, Head,
LeftShoulder, LeftArm, LeftForeArm, LeftHand,
RightShoulder, RightArm, RightForeArm, RightHand,
LeftUpLeg, LeftLeg, LeftFoot, LeftToeBase,
RightUpLeg, RightLeg, RightFoot, RightToeBase
```

**项目根目录 4 个 FBX 是 UE 骨架（23 骨，与此一一同构）：**

```
root, pelvis, spine_01, spine_02, spine_03, neck_01, head,
clavicle_l, upperarm_l, lowerarm_l, hand_l,
clavicle_r, upperarm_r, lowerarm_r, hand_r,
thigh_l, calf_l, foot_l, ball_l,
thigh_r, calf_r, foot_r, ball_r
```

**关键结论**：两者是**一一对应的同构骨架**，重定向**只需名字映射表**，不需要 SMPL、不需要骨骼拓扑推测、不需要 IK 求解器。

### 3.4 标签生成方式

```
目录英文层级  →  中文标签  →  模板扩写出多样化描述
1.7.3.3.Stairs_Up_Down  →  "上楼梯"  →  "走上楼梯" / "慢慢上楼" / "一步一步上台阶"
```
无需人工标注。每类生成 8–15 条中文变体，兼顾语料多样性与语义一致性。

### 3.5 训练数据规模档位

| 档位 | 规模 | 用途 | 预处理耗时估算 |
|---|---|---|---|
| **Tier-S（首版必做）** | 约 40 个细类 × 每类 6–8 条 ≈ **2,500–3,000 条片段**（30fps，150 帧切片） | 2–3 小时出第一版可演示效果 | Z 盘网络读，约 20–35 分钟 |
| **Tier-M（P1）** | 全量 BVH_Body 去重后 **约 12,000 条** | 全量训练，语义覆盖完整 | 约 2–4 小时（可断点续跑） |
| **Tier-L（P2）** | Tier-M + 武术 220 条 | 加入武术套路 | 增量约 10 分钟 |

磁盘估算：Tier-M 特征 ≈ 12,000 × 150 × 260 × 4 B ≈ **1.9 GB**（float32），可接受。

## 4. 技术路线（已定，本 PRD 只做产品化）

```
BVH/FBX 动作数据
   ↓ 解析 + 重采样 30fps + 23 关节
统一运动特征（23 关节旋转 + 根轨迹，约 260 维/帧）
   ↓
MotionVAE（1D-Conv，latent 128）           ← 压缩动作表示
   ↓
潜空间扩散 Transformer（d=256，8 层，约 11M 参数）  ← 学分布
   ↑ 条件：BAAI/bge-small-zh-v1.5（24M，冻结）中文文本向量
   ↓
解码回关节旋转 + 根轨迹
   ↓ 名字映射表（23→23）
UE 骨架 / three.js 预览本地 FBX / 导出 BVH / 导出 UE 动画
```

显存预算：模型 ~11M + VAE ~3M + 文本编码器 24M（冻结，可 CPU/半精度），批量 256 帧。**训练峰值 ≤ 5 GB、推理 ≤ 2.5 GB 在 12 GB 卡上有充足余量。**

## 6. 功能规格要点

### 6.1 中文指令支持范围

| 层级 | 支持内容 | 示例 | 状态 |
|---|---|---|---|
| L1 基础动作类别 | `1.7.Daily_Life_Behavior` 等大类的细类级语义 | "上楼梯"、"扫地"、"喝水"、"梳头"、"搬箱子" | P0 |
| L2 动作变体 | 同一动作的修饰词（速度/方式） | "慢慢上楼"、"快步走"、"小心地放下" | P0（模板内已有变体） |
| L3 武术套路 | 长拳/太极/八极拳/鹤拳/器械 | "打一套陈式太极"、"练一段长拳" | P1 |
| L4 部位控制 | 左右手/腿/上下半身粗粒度 | "挥挥左手"、"抬右腿" | P1（**能力有限，见 6.3**） |
| L5 精确控制 | 指定关节角度/轨迹/节奏 | "左手抬到肩高停 2 秒" | P2 / 当前**不支持** |

**指令长度建议**：4–20 个汉字。过短（"动"）无信息量，过长（> 40 字）超出训练分布。

### 6.2 长动作生成与时长控制

```
目标时长 T 秒 → 帧数 N = 30T
窗口 W = 150 帧，重叠 O = 30 帧，步长 S = W - O = 120 帧
窗口数 K = ceil((N - O) / S)
```

- 每个窗口独立采样，在**潜空间**对重叠区做线性/球面插值融合，避免特征空间平均导致的动作"糊"
- 根轨迹单独处理：以第一窗口为基准，后续窗口做平移对齐 + 一阶平滑
- 生成后做一次整体平滑（可选，强度可调）
- 时长档位：3 / 5 / 8 / 12 秒（P0）；更长（> 20 秒）随 P1-03 放开

### 6.3 局部/身体部位控制的能力边界（诚实说明）

**能做到的：**

- 「挥挥左手」「抬右腿」——如果训练集里有足够多"单侧肢体主导"的动作（挥手、抬腿、踢球等），模型能学到"左手"这个语义，生成**大方向正确**的动作
- 「上半身别动」——当指令与训练集中的"站立/静立"类动作语义接近时有效

**做不到的（当前版本明确不支持）：**

| 做不到 | 原因 |
|---|---|
| 精确到某根骨骼的旋转角度 | 文本向量是全局池化的句子表示，无关节级空间分辨能力 |
| 精确的时序节奏（"抬 2 秒再放下"） | 无时间轴条件通道，模型只学整体时长分布 |
| 未在训练集中出现的部位组合（"右手画圈左手不动"） | 零样本组合泛化能力弱，且训练标签粒度粗（整句对应整段动作） |
| 对身体比例不同角色的精确接触（手扶栏杆） | 无场景物体、无接触约束，纯运动学生成 |
| 保证不穿模（手插进身体/裙摆穿插） | 无碰撞检测、无物理仿真 |

**产品上的处理**：UI 必须在 P1-01 上线时给出内联提示——"部位控制为粗粒度语义引导，不保证精确到位"。**不假装能做到。**

### 6.4 训练数据规模档位

见 §3.5。首版固定走 **Tier-S**，UI 与配置需支持切换档位（`config: tier: S|M|L`），以便后续扩展不需改代码。

## 9. 不做什么（Not in scope，明确排除）

| 排除项 | 原因 |
|---|---|
| **多轮聊天 / 对话式交互** | 交互层只做"指令 → 动作"，不做 LLM 对话（HAST-SEC 的 0.8B LLM 部分不要） |
| **表情、口型、面部动画** | 纯骨骼身体动作，FBX 里没有面部骨骼 |
| **物理仿真 / 碰撞检测 / 布料** | 运动学生成，不保证物理合法；裙子穿模不在首版范围 |
| **SMPL / SMPL-X 体系** | 已有 23 关节同构骨架，走 SMPL 是绕远路 |
| **VRM 格式支持** | 与 HAST-SEC 的核心差异点之一；首版只做 BVH + UE FBX，VRM 留 P2 之后 |
| **实时流式低延迟生成** | 目标时延 ≤ 10 秒（批式），不做逐帧流式 |
| **多人协同 / 云端部署 / 账号体系** | 单机本地作品集工具 |
| **自动绑定（Auto-Rigging）** | 假设输入 FBX 已有骨架 |
| **音频驱动动作**（音乐→舞蹈） | 不在本期 |
| **跨数据集通用泛化**（如任意文字描述都能生成） | 只保证训练分布内的中文指令 |

## 10. 风险与待确认问题

| ID | 风险 | 影响 | 缓解措施 | 待确认 |
|---|---|---|---|---|
| **R1** | **自动生成的中文标签语义粒度粗**：目录层级只到"上楼梯"级，无法区分"扶栏杆上""跨两级上""快速冲刺上楼"；模板扩写的 15 条变体本质是同一动作 | 模型学到的是"类中心"，指令稍具体就失真；盲评容易暴露 | 首版控制预期，UI 提示"指令请贴近训练集已有类别"；保留 Tier-S 类目清单给用户看；P1 引入动作属性（速度/幅度）作为附加条件 | 是否需要为 5–10 个核心类别做人工精标（每类 20 条）？ |
| **R2** | **武术长套路超出单窗口长度**：太极/长拳单条 30–90 秒 = 900–2,700 帧，远超 150 帧窗口 | 长套路被切碎后每段语义不完整，"打一套完整长拳"无法真正实现 | 按"起势/段落/收势"结构切分并加段落标签；生成时按段落序列拼接；P0 只承诺 12 秒，超出时长走 P1-03 | 武术段落的人工切分点是否可接受半自动？ |
| **R3** | **FBX 绑定姿态与 BVH rest pose 不一致导致穿模**：BVH 采集的 rest 接近 T-pose，UE 骨架 FBX 多为 A-pose，且腿长/躯干比例不同 | 直接套用会塌肩、手插身体、脚悬空/穿地 | 名字映射 + rest pose 偏移补偿（每角色算一次 delta 旋转）；加"体型缩放因子"；P2 引入足部 IK | 4 个 FBX 的 rest pose 需逐个实测并记录到映射表 |
| **R4** | **Python 3.13 与 torch / CUDA 兼容性**：生态对 3.13 支持较新，可能无对应 wheel 或 `torch.compile` 不稳定 | 环境装不起来，项目 0 进度 | 优先试 3.13；不可用则退回 3.11/3.12 独立 venv（仍在 D 盘内，不影响硬约束）；**这是 P0-01 的第一件事，必须先验证再写其他代码** | **需立即确认**：在本机 3.13 上 `pip install torch --index-url .../cu121` 是否成功 |
| **R5** | **Z 盘网络读取速度导致预处理缓慢**：26k 文件、总量可能达数百 GB，逐个读 header 都要等待 | Tier-M 预处理可能需要数小时甚至更久，超出 2–3 小时目标 | 首版只用 Tier-S（约 3,000 文件）并**只读文件头 + 按需读取所需帧段**；并发读取（8–16 线程）；一次预处理后特征全落 D 盘，后续不再碰 Z | 需实测 Z 盘单文件读取耗时与并发上限 |
| **R6** | **文本条件太弱，生成结果"语义漂移"**：24M 冻结编码器 + 11M 扩散模型容量有限，文本向量可能被动作分布淹没 | 输入不同指令出相似动作（mode collapse） | 提高 classifier-free guidance（3–5）；对比实验：有文本条件 vs 无条件，验证指令可分性；若失败则加大文本条件投影层 | guidance 需在验证集上扫一遍 |
| **R7** | **2–3 小时出效果的进度风险**：环境 → 预处理 → VAE → 扩散 → 前后端，任一环节卡住都会超时 | 无法达成 S1 演示目标 | 严格分级：Tier-S 极小子集（10 类 × 5 条 = 50 条）先跑通全链路，再扩到 3,000 条；每一步都有"最小可跑版本" | 是否接受"50 条数据 + 5 个类别"的超小 demo 作为 2 小时里程碑？ |
| **R8** | **导出 UE 动画的实际可行性未验证**：没有 UE 工程文件，导出格式（FBX vs 自定义 JSON + 导入脚本）路径未定 | P0-14 可能做不完 | 优先导出**标准 FBX（含 23 骨动画）**，UE 可直接导入；备选：导出 JSON + Python 脚本在 UE 内生成 AnimSequence | 用户是否有可用的 UE 5.x 环境？是否接受 FBX 导入方式？ |
| **R9** | **单角色 4 个 FBX 的骨骼命名/层级细节可能与假设不符**（如 `ball_l` 是否存在、是否有额外辅助骨） | 重定向映射表 23/23 对不上 | P0-04 第一步就是**用脚本读 4 个 FBX 的实际骨骼列表并生成映射表**，以实测为准 | 需实测确认 4 个 FBX 骨骼数与命名 |
